当前最值得优先验证的差异：

1. **sing-box 客户端 TUN 栈**：fork 的 `sball()` 显式生成 `stack: gvisor`，本次读取的上游未设置该字段。只有实际使用该 JSON 的 sing-box TUN 客户端才与此项直接相关；Mihomo 用户不能据此解释性能下降。
2. **自动选择候选集合**：fork 将启用的 Trojan/Snell 节点追加到客户端策略组。即使原有规则不变，自动选中的协议也可能改变。
3. **菜单阻塞链**：主菜单在接受输入前同步查版本、查公网 IP 和地区；已安装时又通过 `showprotocol() → sbymfl() → v4v6()` 重复查询。脚本版本请求没有显式总超时。
4. **上游也有的设置**：主要客户端 DNS、分流规则，以及 Mihomo 的默认轮询负载均衡都来自上游。它们值得诊断，但不能直接认定为 fork 新增回归。

### 1. 任务与判断原则

用户报告：

- 规则代理模式下网页加载慢，怀疑分流规则存在问题；测速明显慢于 fork 的上游项目。
- 在 VPS 上使用管理脚本时，加载菜单、进入选项或返回菜单耗时过长。

把上述内容作为需要复现的现象，不预设“规则写错”就是根因。分别处理：

| 现象 | 必须区分的指标 |
| --- | --- |
| 网页慢 | DNS、连接/TLS、TTFB、关键资源完成时间、失败重试 |
| 测速慢 | 客户端 URL 延迟测试、单连接吞吐、多连接吞吐；分别记录 ms、MB/s 或 Mbps |
| 菜单慢 | 启动到可接受输入、选择到下一菜单可接受输入、实际操作完成时间 |

先建立证据，再做最小修改。规则代理功能需要保留，不能通过改成全局代理、清空规则、关闭所有 IPv6 或删除协议来宣布问题解决。不要开展与这两个问题无关的重构。

### 4. 第一阶段：建立可比较的基线

先保存当前脱敏配置、版本、命令和复现结果。以固定一个双方共有的原有节点为主基线，优先选择用户实际使用的协议。保持 VPS、客户端、客户端内核、服务端内核、节点参数、测试目标、缓存状态和并发数一致。

先只切换客户端生成配置；若问题仍指向服务端，再固定客户端单独比较服务端配置。不要同时更新内核、切换节点、改 DNS 和改 TUN 栈。

建立下面的最小实验矩阵，按结果逐步扩展：

| 实验 | 固定条件与唯一主要变量 | 回答的问题 |
| --- | --- | --- |
| A | 上游配置，规则模式，固定原有节点 | 可复现的上游基线 |
| B | fork 配置，规则模式，同一节点 | 是否存在 fork 配置回归 |
| C | fork 配置，全局模式，同一节点 | 规则/DNS 路径是否参与；只作诊断对照 |
| D | fork 规则模式，当前自动组/负载均衡组 | 差异是否来自选到另一协议/链路 |
| E | 仅 sing-box TUN：保持 B，只改变实际版本支持的 stack 设置 | TUN 栈是否限制吞吐或增加 CPU 开销 |
| F | 在有证据指向 DNS、IPv6 或传输层时，每次只改变一项 | 验证具体假设 |

客户端路径要求：

- `clmi.yaml` / Mihomo：优先 A–D，不能把 JSON 的 `gvisor` 当作其瓶颈。
- `sbox.json` / sing-box TUN：A–E；按该内核版本核实栈默认值及支持范围。当前官方文档已包含 1.15 的栈变化，不得用旧版经验推断全部版本，也不要为实验擅自升级内核。
- 单节点链接：读取客户端自己的规则与覆写；先检查节点和服务端变化。

网页用实际慢站点及关键资源作为主目标，并加入一个预期直连目标、一个预期代理目标。记录命中的规则、最终出口/协议、HTTP 状态、失败率、TTFB、加载完成时间及必要的浏览器 HAR。脱敏 HAR 中的 cookie、认证头和订阅凭据。

网络测试采用交错顺序 A/B/A/B，网页每组至少 10 次，冷/热缓存分开；吞吐每组至少 5 次，分别记录单连接和固定并发结果及流量总量。报告样本数、p50、范围；需要 p95 时至少补足 30 个样本并注明样本量。URL 延迟不能替代带宽结论。

提供可复制的采集命令或小脚本，至少记录 curl 的 `time_namelookup`、`time_connect`、`time_appconnect`、`time_starttransfer`、`time_total`、`speed_download`、`size_download`、状态码与退出码。

测量解释必须正确：

- curl 时间字段大多是从请求开始累计的时间，不能直接相加。
- 显式 HTTP/SOCKS 代理下，TCP 连接时间可能只是到本地代理；`socks5h` 的目标域名解析在代理侧。不能将其 `time_namelookup` 当作完整目标 DNS 延迟。
- 当前 YAML 的 `port: 7890` 是 HTTP 代理端口，不能未经检查就当作 SOCKS 端口；当前 JSON 以 TUN 为入口，也不能凭空假设有 SOCKS 监听。
- HTTP/SOCKS 请求只用于隔离链路；原始症状如果在 TUN 下，最终必须在 TUN 下复验。`--noproxy` 不能保证绕开系统 TUN 路由。
- 记录重定向和实际下载字节。不要用错误页、204 小响应或不同测速服务器比较吞吐。

### 5. 第二阶段：优先修复菜单阻塞

目标：已安装用户执行 `sing_box` 后，能够迅速选择操作；外部版本站、IP 查询站失效时仍可操作菜单。

采用最小充分方案，优先顺序如下：

1. **菜单首次展示只读取必要的本地信息。** 脚本版本、内核版本、服务状态、配置中的端口/域名可本地读取；未实时探测的公网状态明确显示“未探测”，不能伪装成“可用”或“不可用”。
2. **把联网检查移到对应动作。** 更新脚本/内核时获取最新版本；用户要求刷新 IP、诊断连通性或查看详细联网状态时再探测。保留原有功能入口或增加一个最小明确入口，并更新说明。
3. **分离 `sbymfl()` 中本地分流信息与远端探测。** `showprotocol()` 不应为展示现有规则而触发 SOCKS 查询与第二轮公网探测。
4. **修复相对目录依赖标记。** 使用稳定的绝对状态位置；旧标记、现有安装和必要命令存在性应有明确迁移策略。标记缺失不应让正常打开菜单运行全系统更新；安装/修复依赖时才执行必要包管理操作，成功后才写标记。
   同时检查顶层 OpenVZ TUN 初始化和 `ping 10.0.0.2` 的回退探测：打开菜单不创建设备、不改 crontab、不探测远端来推断展示字段；相关初始化移至实际需要它的安装或修复动作。
5. **网络请求按用途设置预算。** 交互元数据请求有连接超时和总超时，失败返回清晰状态；同一次动作重复使用已取得的 version 响应。二进制下载保留适合大文件的预算，不能统一缩成几秒。
6. **检查重入与固定等待。** 部分返回路径执行外部 `sing_box`，会重新运行整个脚本；部分函数调用自身。先消除重复初始化的实际代价，必要时局部改为循环，不为此重写全部菜单。静默生成订阅时跳过纯展示用 sleep，保留有真实异步依赖的等待。

不默认增加后台线程、定时刷新、持久缓存或复杂状态框架。优先“按需请求 + 本次调用复用 + 明确超时”。如确实需要缓存，先说明它解决的已测瓶颈，并明确有效期、失败行为和失效条件；不得把展示缓存用于覆盖节点公网地址。

保留现有正确性：IPv6 接口配置与公网可达性分开显示；公网探测双失败时保留原节点地址；保留非交互 `printf ... | sing_box` 的输入顺序、正常退出、EOF 和退格输入行为。

### 6. 第三阶段：按证据修复规则代理和测速回归

逐项验证，未被证实的假设不进入正式补丁。

**6.1 节点选择与新增协议**

Mihomo 当前模板的默认候选中含轮询负载均衡；自动组用 URL 健康测试，它们不是带宽测试。先读客户端实际策略状态，记录每轮最终节点，不能仅从 YAML 顺序推定用户当前选择。

比较固定原有节点、原有候选集合和新增 Trojan/Snell 后的集合。若只在动态组下变慢，定位实际被选中的协议和失败/吞吐差异，再调整默认策略或候选纳入方式。保留新协议可手动使用，不能为了结果直接删掉它们。任何默认策略变化都要解释实际行为和老用户影响。

**6.2 TUN 栈**

只在实际使用 sing-box TUN 时做 `gvisor` 与该版本支持的默认/其他栈对照，同时记录 CPU 占用、吞吐、TCP/UDP 连通性。只有证据支持且目标系统兼容时才改模板。不得把“换某个 stack 一定更快”写成结论。

**6.3 DNS 与分流**

对慢请求还原“域名 → DNS 服务器及其出口 → 命中规则 → 最终节点/直连”。具体检查：

- 节点域名和 DoH 服务器的 bootstrap 解析是否可完成，是否存在代理解析的循环依赖。
- DNS 是否遵循路由，国内直连业务是否绕到高延迟 DNS/出口；只有记录支持时再调整 `nameserver-policy`、direct resolver 或对应 sing-box DNS 规则。
- fake-IP、域名映射、嗅探与实际入口是否配合正确；不要无证据统一打开或关闭嗅探。
- GeoSite/GeoIP 规则集能否下载、是否持久缓存、首次与后续加载是否不同；不要把启动下载慢混同于每个请求规则匹配慢。
- 国内、国外、私网、用户自定义例外及最终兜底是否符合既有预期；输出“预期出口/实际出口/命中规则”表。
- IPv6 是否实际可达，AAAA 与连接回退是否导致等待；分别测 IPv4/IPv6，再决定局部策略，不全局禁用掩盖问题。
- DNS/规则字段是否适配客户端实际内核。服务端版本不能代替客户端版本，JSON/YAML 语法正确不能代替内核配置校验。

**6.4 持续吞吐仍慢时**

在固定节点、相同目标和稳定 DNS 后，检查客户端/VPS CPU、TCP 重传、丢包、MTU/PMTU、UDP/QUIC 可达性、协议参数、是否经 CDN/Argo/WARP。先识别限制发生在哪一段，再决定调整。不要批量套用 BBR、MTU、连接复用或缓冲区“优化参数”。

先复用现有 `tests/shell_testlib.py` 的函数抽取和临时目录方案。`sb.sh` 顶层包含包安装、服务管理和系统配置副作用，禁止为测试方便直接 `source sb.sh`，也不要在当前开发机以 root 执行完整安装器。

**菜单测试：**

### 8. 验收标准

以下时间和比例是本任务的建议工程目标，不是已经测得的效果。先测基线；若设备性能或测量噪声不允许，给出证据和合理调整，不捏造达标结果。

| 项目 | 验收要求 |
| --- | --- |
| 已安装菜单首个输入点 | 同机正常/断网条件下至少 30 次，p95 ≤ 2 秒；普通展示的公网请求与包管理器调用均为 0 |
| 子菜单切换/返回 | 纯本地展示和返回的 p95 ≤ 1 秒；用户明确进入版本/IP 联网刷新、安装、下载或测速动作后，按该动作声明的预算验收；无重复初始化等待 |
| 版本/IP 主动刷新 | 有明确总预算；成功、失败、未探测状态不混淆；失败仍能返回菜单 |
| 原有节点性能回归 | 同环境固定原有节点，修改后单/多连接吞吐中位数分别达到上游可比基线的至少 90%；若噪声超过 10%，增加交错样本后判断 |
| 网页性能 | 原始慢网页可复现问题消失或显著改善；固定同路由情况下 p50 TTFB/加载时间不出现超过 10% 的稳定回退；记录故障率，不只看均值 |
| 分流功能 | 测试目标的预期出口与实际出口一致，保留规则模式、私网访问和用户例外 |
| 配置与发布 | 生成器输出通过对应内核校验；失败保留旧文件；VPS 刷新和客户端刷新后确认新配置实际生效 |

如果只有源码环境：可以完成菜单阻塞的离线复现、修复和测试，交付配置对照与网络采集工具；网页和带宽结论必须标记为待实测。没有真实链路数据时，不强行提交猜测性的 DNS/stack/协议调优。

### 9. 修改、部署与回滚边界

- 优先修改 `sb.sh` 的模板/函数与相应测试；不能只改一次生成的 `/etc/s-box/clmi.yaml` 或 `sbox.json`，下次刷新又恢复。
- 将菜单修复与已证实的代理性能修复分成可独立审查的变更；保留自定义 HTTPS 订阅、令牌、Trojan/Snell、老命令兼容和失败保留原配置行为。
- 不默认批量升级内核、重装 VPS、调整系统 DNS/防火墙或全量同步上游。
- 本任务授权仓库内诊断、修改和测试；推送远端、公开 PR、生产部署和重启服务以用户已有授权为准。先准备可审查补丁与部署命令，不擅自影响现有连接。
- 给出具体部署/回滚步骤：备份脚本与相关配置 → 校验候选版本 → 更新脚本/必要配置 → 重新生成订阅 → 客户端刷新并确认生效 → 复测。没有服务端配置变化时不为客户端模板修改而重启服务。
- 说明菜单 7 会从远端 `main` 获取脚本：本地未推送版本可能被覆盖。回滚保留凭据、节点地址及用户自定义规则，不靠卸载重装。
